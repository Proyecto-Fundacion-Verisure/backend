### 6. `service/AuthService.java` + `AuthServiceImpl.java`
Interfaz:
```java
void verify(String token);
Long resendVerification(String email);
```

Impl (`AuthServiceImpl`, `@Transactional`):
- `registerPartner`: antes de guardar el `User`, fijar `createdAt`, `verificationToken` y `verificationTokenCreatedAt` (UUID aleatorio).
- `verify(token)`:
  - token nulo/vacío o `findByVerificationToken` vacío → `DomainException(VERIFICATION_EXPIRED)`
  - `verifiedAt != null` (ya usado) → `VERIFICATION_EXPIRED`
  - `createdAt + 24h < now` o `verificationTokenCreatedAt == null` → `VERIFICATION_EXPIRED`
  - éxito: `verifiedAt = now`; si `status == PENDING_VERIFICATION` → `PENDING_APPROVAL`; guardar.
- `resendVerification(email)` → devuelve `Long?`:
  - `findByEmail` vacío o `status != PENDING_VERIFICATION` → `null` (204 silencioso, sin enumeración de usuarios)
  - si no: regenerar token + `verificationTokenCreatedAt = now`, guardar, devolver `user.getId()`.
- Generador: `UUID.randomUUID().toString()`.

### 9. `repository/UserRepository.java` — consultas
```java
@Query(value = """
    select new com.verisure.backend.dto.orgaccount.OrgAccountRow(
        u.id, p.name, p.cif, u.fullName, u.email, p.phone,
        coalesce(u.createdAt, p.createdAt), u.status,
        case when u.verifiedAt is null then false else true end)
    from User u
    left join u.partner p
    where u.role = com.verisure.backend.entity.enums.Role.PARTNER
      and u.status in :statuses
    order by coalesce(u.createdAt, p.createdAt) asc
    """,
    countQuery = """
    select count(u.id) from User u
    where u.role = com.verisure.backend.entity.enums.Role.PARTNER
      and u.status in :statuses
    """)
Page<OrgAccountRow> findAccounts(@Param("statuses") List<UserStatus> statuses, Pageable pageable);

long countByPartnerIdAndStatus(Long partnerId, UserStatus status);
```
Imports: `UserStatus`, `Page`, `Pageable`, `OrgAccountRow`.

Filtro `status` del GET:
- `null` / vacío / `PENDING` → `[PENDING_VERIFICATION, PENDING_APPROVAL]` (ambos estados pendientes, lo que pide el frontend).
- cualquier `UserStatus` → ese estado.
- otro valor → `DomainException(VALIDATION_ERROR)` (400).

### 10. `service/OrgAccountService.java` + `OrgAccountServiceImpl.java` — nuevos
Interfaz:
```java
Page<OrgAccountRow> list(String status, Pageable pageable);
OrgAccountRow approve(Long userId);
OrgAccountRow reject(Long userId);
```

Impl (`readOnly` a nivel de clase; `@Transactional` en approve/reject):
- `approve`: user → `ACTIVE`; si `partner != null && partner.status != ACTIVE` → `ACTIVE`. Devuelve fila.
- `reject`:
  - user → `REJECTED` y `save` (el flush de la siguiente consulta ya lo cuenta como no activo).
  - `partner != null && partner.status == PENDING && countByPartnerIdAndStatus(partner.id, ACTIVE) == 0` → `partner = REJECTED`.
  - Un `Partner` ya `ACTIVE` se queda `ACTIVE` aunque este fuera su único usuario (regla de la tarea).
- `findOrThrow`: `NotFoundException.of("User", userId)`.
- `toRow(user)`: usa `user` y `user.getPartner()`; `requestedAt = coalesce(user.createdAt, partner.createdAt)`; `emailVerified = user.verifiedAt != null`.

### 11. `controller/OrgAccountController.java` — nuevo
`@RequestMapping("/api/admin/org-accounts")`, inyecta `OrgAccountService` + `NotificationService`:
- `GET` → `Page<OrgAccountRow>` (`@RequestParam(required=false) String status`, `Pageable`). Sin `sort` en `PageableDefault` (no hay propiedad `requestedAt` en las entidades).
- `PATCH /{id}/approve` → servicio + `notifyOrgAccountApproved(id)` fuera de tx → 200 fila.
- `PATCH /{id}/reject` → servicio + `notifyOrgAccountRejected(id)` fuera de tx → 200 fila.

## Verificación contra los «hecho cuando»

| Criterio | Implementación |
|---|---|
| El enlace verifica y deja la cuenta pendiente de aprobación | `verify()` → `PENDING_APPROVAL` |
| El mismo enlace usado dos veces falla | `verifiedAt != null` → `VERIFICATION_EXPIRED` (410) |
| Un token caducado devuelve 410 | comprobación 24 h → `VERIFICATION_EXPIRED` |
| Verificado pero sin aprobar, el login sigue rechazando | `CustomAuthenticationManager` → `ACCOUNT_PENDING_APPROVAL` (ya existía) |
| Aprobar deja entrar | `approve` → user y partner `ACTIVE` |
| Rechazar no | `reject` → `REJECTED` |
| Avisos fuera de la transacción | `notifyOrgAccountApproved/Rejected` desde el controlador |
| Aprobar 2º usuario de entidad existente no crea segunda entidad | dedup por CIF en `registerPartner` (B1-14) + approve solo normaliza partner a `ACTIVE` |
| Rechazo con CIF existente solo toca ese `User` | solo demote a `REJECTED` si partner PENDING sin usuarios activos |
